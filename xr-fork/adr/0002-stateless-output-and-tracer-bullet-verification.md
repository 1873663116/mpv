# ADR 0002 — 常驻纹理出口无状态化 + 曳光弹验证策略

状态:Accepted
日期:2026-06-08
范围:Enchron / XrPlayer 的 mpv fork(`enchron` 分支),阶段 1

## 背景

阶段 1 要验证「常驻纹理出口」(见 ADR 0001)。两个设计问题浮现:

1. **验证可信度**:最初设想"渲染到 IOSurface → 读出存 PNG"。但 PNG 只验证了
   "mpv → IOSurface" 半段,**没有验证真正的目标**:"IOSurface 能否被 RealityKit 拿去做
   3D 纹理呈现"。验证必须覆盖真正的风险面(RealityKit 那端),否则不可信。
2. **无帧等边缘状态的归属**:"无可用帧" 在出口层是一个症状,它可能对应播放结束、卡顿、
   缓冲、异常等多种语义。这些语义与播放核心 / 事件系统重合,但二者本应解耦。

## 决策

### 1. 验证用「曳光弹 / 垂直切片」,不用 PNG

阶段 1 = 一条贯穿全栈的最小切片:**libmpv(改过)→ IOSurface → macOS RealityKit 实时呈现**。
- 验证夹具:一个最小 macOS app(SwiftUI + `RealityView`),内嵌 libmpv 自动播测试视频,
  视频实时贴在一个**固定斜角长方体**上。双击即跑。
- 夹具带验证用假开关:`Window` 分支关闭 resident 出口,mpv 走正常窗口管线;
  `Immersive` 分支开启 resident 出口,RealityKit 采样 Swift 提供的 IOSurface。
- 夹具位置:`xr-fork/verify/`(隔离于上游,链接我们编的 libmpv)。
- 用**斜角长方体**而非正对平面:正面平面与"窗口直接播视频"视觉无法区分,是**假阳性**;
  斜角透视能证明纹理确实穿过了 RealityKit 的 3D 渲染管线。

### 2. 常驻纹理出口**无状态**

出口只做一件事:**有帧 → 渲染进 IOSurface;无帧 → 保持上一帧(不更新)**。
它**绝不**判断"这是结束 / 卡顿 / 异常"。这些语义由 mpv **已有的事件 / 属性系统**承载
(`end-file`、`eof-reached`、`core-idle`、`paused-for-cache` 等),Enchron 的 Swift 层
(`MPVPlayerAdapter` 事件循环)本就在订阅。

后果:**维持「核心报告事实 / 出口只渲染」的解耦**;出口的边缘情况坍缩为仅两个——
`无帧 → 保持/跳过`、`尺寸变化 → 重建纹理`,其余全部"由已有事件系统照常处理,出口不掺和"。

### 3. 测试分层

- 视觉正确性 → 验证夹具人眼 +(可选)自动截图比对。
- IOSurface 创建/导入/渲染 成功失败 → 运行时断言 + 日志。
- 无帧/尺寸变化 → 夹具里手动制造(播到尾、换分辨率)观察。
- 不写重型测试套件:风险在 GPU/视觉/平台互操作,单元测试帮不上。

## 考虑过的替代方案

| 方案 | 否决理由 |
|---|---|
| 渲染到 IOSurface → 读出 PNG | 只验半段;验不了"RealityKit 能否用它呈现",不可信 |
| 横向分层(先全 mpv,再全 RealityKit) | 接不上时才发现,反馈太晚;曳光弹先打通全栈再加厚 |
| 正对平面验证 | 与窗口直接播视频视觉无法区分,假阳性 |
| 出口自行处理结束/卡顿状态 | 重复造已有事件系统,破坏核心/出口解耦 |

## 后果

- 阶段 1 与阶段 2 的 RealityKit 部分有意重叠:曳光弹本身就是最小 RealityKit 集成,
  也是最终 "libmpv 链进 Swift app" 形态的预演。
- 阶段 1 需要 libmpv 构建(`-Dlibmpv=true`)+ 一个 Swift app,工作量大于 PNG 版,
  但换来端到端可信验证。
